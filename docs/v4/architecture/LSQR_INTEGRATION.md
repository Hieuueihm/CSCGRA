# LSQR integration — architecture and implementation contract

This stage connects the selected LFSR/Phi/B architecture to a complete bounded
LSQR solve. The previous [Vivado baseline](../../../reports/v4/rtl_vivado_audit_20260909/evidence.json)
remains the accepted source snapshot until this stage passes its own gate.
Numeric formats remain D18F14/C18F16/S27F22/X24F20/ACC64 candidates, with normal
residual tolerance 1e-5 and at most 128 candidate updates. RTL verification uses
Vivado xvlog/xelab/xsim only. No synthesis/implementation is authorized yet.

## Ownership and reuse

The new solver composition has one `operator_memory`, one `kernel_engine`, one
scalar service, one generic service-program sequencer and one transactional
result writer. `operator_memory` owns the existing live LFSR generator, one
8-bank Phi cache, one dense B cache and support_builder, with exclusive fill,
build and compute ownership. `kernel_engine` owns exactly two existing 4×4
PE arrays and one working vector store. There are no additional multipliers
for LSQR vector/scalar products outside the PE arrays.

The functional RTL names contain no version label. `v4` is the directory name;
generated definitions use the `CSR_` namespace. The complete host/recovery
wrapper is reserved as `csr_top`; the bounded solver is `lsqr_engine`.
See the [module catalog](MODULES.md) and [diagram](../diagrams/lsqr.mmd).

The earlier `resident_engine` remains a separately tested context/GEMV reference.
It is not instantiated beside kernel_engine in a solver bitstream. This avoids
duplicating PEs or resident matrices. The full recovery/host top is still a
separate integration layer; a complete LS solve does not imply eleven recovery
programs or an AXI/DMA shell are implemented.

The service-program PC selects generic kernels and scalar operations. Kernel
local FSMs implement bounded address/route schedules; they do not choose LSQR
recurrence, convergence or iterations. Service instructions are an explicit
candidate extension, separate from the old tile64/control256 image ABI. They
must be generated and validated, with source/image hashes and observable PC
traces. No hidden Python decisions may occur after a solve starts.

## Generic datapath contract

Working storage contains 16 vectors, each at most 128 S27 values, striped over
32 banks. Two read ports support elementwise binary kernels. A destination is
published only after the complete kernel succeeds; source/destination aliases
must be safe and partial candidates cannot become valid vectors. Host preload
and inspection are idle-only. Matrix geometry and key/generation/job/format
are checked before compute ownership begins.

| Kernel | Required arithmetic |
|---|---|
| ZERO/COPY | Produce or copy one bounded vector |
| ADD/SUB | Checked S27 elementwise arithmetic on the PE array |
| SCALE | S27×S27, round ties away once by 22 bits |
| NORMALIZE | S27×reciprocal S27, round ties away once by dynamic exponent e |
| GEMV_B | B or B-transpose, C18×S27, checked ACC64, final round by 16 bits |
| ENERGY | Sum of vector squares in raw ACC64; no intermediate S27 rounding |
| NARROW_X | S27F22→X24F20, then exact re-embedding into S27F22 |
| SCALAR_MUL | One PE lane performs checked S27×S27 with round by 22 |
| SCALAR_ENERGY | Two PE lanes square scalars; checked sum in ACC64 |

For normalization, e=bit_length(norm), reciprocal=round((2^e/norm)*2^22).
The vector result is round(vector_raw*reciprocal_raw / 2^e), not an ordinary
S27 multiplication followed by another shift. The distinction preserves the
existing numerical model for small norms.

## Program and certificate

The independent authority is `models/v4/lsqr.py::least_squares`. The program
performs zero initialization, B-transpose-y reference energy, normalized initial
Golub–Kahan vectors, the complete next bidiagonal pair, Givens rotation, x/w
updates, and a certificate after every stored candidate. It preserves each
intermediate rounding point rather than fusing scale/subtract operations.

The current compiler emits 84 meaningful 128-bit instructions and pads the
256-word image with FAIL. PC0 initializes the solve, PC19 starts an iteration,
PC41 starts the Givens steps, PC74 handles the final certificate path, and
PC82/83 return success/failure. Labels are generated by `lsqr_program()` and
must be used when the program changes. The vector workspace and scalar RF
allocations are separate from the PE-local RF8; the kernel owns transfers
between these levels.

The reference normal energy is ||B-transpose-y||². For stored candidate X, form
r=y-BX and g=B-transpose-r, using that same stored X. Pass iff
`energy(g) * 10000000000 <= reference_energy`, evaluated without overflow or
floating-point rounding. A sequential constant shift/add comparator may be
used; it is a scalar comparison, not another vector multiply engine.

Zero beta, zero alpha and zero rho all go through the same stored-X certificate.
A failed certificate with breakdown or exhausted iteration budget reports
nonconvergence. Numeric overflow, divide-by-zero, malformed program/identity or
source faults fail the job; no tolerance relaxation or clipped success is allowed.

## Publication and cancellation

Input measurement is normalized before D quantization; the load boundary must
validate the selected D18 representation and exponent [-31,31]. All working
vectors and committed X stay in the normalized domain. Output carries its
normalization exponent and ordered support indices; the host decodes raw X and
undoes the exponent. This stage does not infer or silently change the basis.

After certificate success, stream exactly the stored X candidate to the result
writer. The sequencer returns the certified candidate slot; the top captures
that slot and uses it for every output read. Validate complete ordered blocks,
mask/tail, tags, X range and exact
S re-embedding. A separate successful commit decision atomically publishes the
candidate bank. Fault or cancel invalidates the candidate but preserves the
previous committed result. A pending output read keeps its captured payload
stable even if a newer result is published. Reset explicitly clears validity.

The accepted approval edge is the publication point. Cancel before that edge
discards the candidate. Cancel after publication preserves both the committed
bank and its successful completion; it must not report a discarded result.

The measurement loader accepts zero or normalized D18 values in [-8192,8192],
checks full ordered blocks and embeds them exactly by shifting eight bits.
The host is responsible for choosing the normalization exponent before load.
The RTL cannot prove that supplied data and exponent correspond to an original
unscaled signal. External normalization exponent and the dynamic reciprocal
shift used inside NORMALIZE are independent quantities.

## Scheduling costs and current limits

The program selects generic kernels; each kernel emits tile operations to the
same 32 PEs. GEMV uses the R1 bank schedule in both directions. For O outputs
and K reduction elements, there are ceil(O/32)*K MAC frames. A 128x96 B uses
384 frames in either direction, with all 32 arithmetic lanes useful per frame.
Small/tail problems leave lanes inactive. This fraction does not measure PE
activity across all clock cycles.

One matrix frame is outstanding at a time. Workspace reads, operand alignment,
PE issue/retirement and candidate publication add cycles around arithmetic.
ENERGY captures parallel raw squares, then reduces them through one registered
65-bit adder, one active lane per cycle. This avoids a long combinational
32-input carry path but exposes a reduction latency. DIV/SQRT and each stored-X
certificate also serialize dependent steps. There is no overlap or timing claim.

Initial optimization candidates are bounded matrix prefetch, overlap of operand
reads with execution and a pipelined energy reduction. They require measured
cycle/stall attribution and the same numeric/ownership tests. Neither a
32-bank layout nor using all lanes in a MAC frame proves high job throughput.
BRAM/DSP inference, actual 100 MHz timing and novelty ablations remain pending.

## Required correctness evidence

Compare actual RTL raw X, iterations, scalar/kernel outputs and certificate
energies against the existing integer model, plus independent SVD diagnostics.
Use live LFSR→support_builder→B for supported measurement cases and explicit
dense B for analytic/rank-stress cases. Cover nontrivial multi-iteration solves,
nonzero residuals, tiny/maximum shapes, low amplitude, zero RHS, breakdown,
nonconvergence, X rounding, overflow and held results. Inject stalls and cancel
in compute, scalar, candidate write and commit phases; verify old results remain
readable and source ownership cannot leak between jobs.
