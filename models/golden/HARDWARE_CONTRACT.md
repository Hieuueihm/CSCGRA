# Hardware-aware fixed-point contract

The repository keeps two deliberately independent numerical contracts:

1. `canonical_fixed.py` is the algorithmic reference. It is frozen, does not
   inspect RTL, and defines the textbook support/update semantics in Q16 with
   signed-24-bit saturation.
2. `hardware_fixed.py` is the implementation contract used by the RTL trace.
   It preserves the algorithmic phases but makes the hardware choices
   explicit: one active LS request, PE0-to-PE3 ingress, four-row service,
   Q16 normal equations, `+1` diagonal regularisation, LDLT without pivoting,
   Q32 reciprocal-D, and signed-24 coefficient writes.

The second contract is not a replacement golden and is not generated from RTL
output. It is an independent reimplementation of the intended datapath. This
keeps a numerical mismatch diagnosable: a failure against `canonical_fixed`
means algorithmic semantics changed; a failure against `hardware_fixed` means
the RTL schedule, fixed-point boundary, or solver implementation changed.

`hardware_abstract.py` exposes the controller-visible phase sequence for the
CoSaMP LS migration. Its manifest is generated by
`run_hardware_abstract.py` and is intentionally separate from
`abstract_rtl_trace_manifest.json`:

```text
canonical_fixed.py -> abstract_rtl.py       -> canonical phase manifest
                  -> hardware_fixed.py
                  -> hardware_abstract.py  -> hardware RTL phase manifest
```

The K16 entries are useful as architectural traces, but are marked
`rtl_capacity_supported: false` because the current support/LS memories are
16-entry hardware. They must not be presented as a K16 RTL sign-off result.

Checks:

```powershell
python models/golden/run_hardware_abstract.py --check
python models/golden/run_abstract_rtl.py --check
```
